## 1 — هوية وعضوية موثوقتان

**حالة التنفيذ المحلي:** أضيفت خدمة قراءة للحسابات القديمة، وهوية وعضوية منفصلتان للحسابات الجديدة، وتحقق من الجلسة والعضوية في HTTP وSocket، ودخول الواجهة برمز الشركة، وعزل المخزن المحلي. التفاصيل والقيود وخطة الطرح في `identity-and-tenancy.ar.md`. لم يحدث نشر أو ترحيل لحسابات العملاء؛ شروط الجرد والاستعادة والقواعد المنشورة لم تغلق بعد، لذلك لا تعد المرحلة مكتملة تشغيلياً.

التبعيات: جرد أماكن `users` ونجاح الاستعادة. الملفات القائمة: `controllers/auth.controller.ts`, `controllers/users.controller.ts`, `utils/currentUser.ts`, `utils/jwt.ts`, `utils/tenantContext.ts`, `app.ts`, وملفات الدخول وAxios في الواجهة.

- إنشاء هوية ثابتة وعضوية تربط الشخص بالشركة ودوره. احسم تعارض أسماء المستخدمين المتكررة عبر الشركات دون دمج هويات تلقائياً.
- حسابات الجذر الحالية لا تمنح وصولاً لجميع الشركات. تربط بعضوية الشركة الحالية التي يثبتها الجرد.
- دخول الشركة التجريبية يبحث في العضوية الصحيحة؛ يمنع البحث العام في كلمات مرور الشركات أو اختيار الشركة بتشابه اسم المستخدم.
- تجزئة كلمات المرور مع توافق زمني محدد للسجلات القديمة، وبعد إثبات النسخ. لا يُنقل hash للواجهة.
- `Authorization` الموثق هو مصدر الهوية؛ إلغاء fallback لدور أو مستخدم من ترويسات الطلب.
- اختيار الشركة النشطة يستلزم فحص العضوية على الخادم، وكذلك صلاحية العضوية بعد إلغائها. غياب السياق لا يسمح بقراءة `default` تلقائياً.
- تحديث الواجهة والجلسة قبل إزالة توافق رموز العملاء القديمة؛ أي توافق لرمز قديم يقيد بشركته المعروفة على الخادم.

اختبارات القبول: رمز غير صالح/منتهٍ، دور مزور، مستخدم محذوف، عضوية ملغاة، شركة غير عضو فيها، مستخدم واحد بعضويتين، أسماء دخول متكررة. لا تُعلن هذه المرحلة منجزة باختبار رمز يحمل `tenantId` فقط.

## 2 — حراسة المداخل وحدود البيانات

**حالة التنفيذ المحلي:** أضيفت حراسة مركزية لكل API، وربط إجراءات الأعمال بصلاحيات الصفحات الحالية، وحراسة إجراء المسودة في Socket، وفصل مراجع الجذر عن غلاف الأعمال. أوقف التصدير الشامل وترحيل المستودعات عبر GET، وصارت قراءة الحسابات بلا كتابة وتهيئتها صريحة تحفظ الموجود. AI يحتاج صلاحية واستحقاقاً صريحاً للشركة وسياقاً محدوداً، وتحديث الواجهة يمر بالخادم الموثق. التفاصيل في `api-authorization.ar.md`. عولج لاحقاً رجوع قراءة الهوية إلى ذاكرة SDK بقراءة REST مباشرة واختبارات انقطاع HTTP في `tenant-data-provider.ar.md`. لا تزال قواعد Firebase والاستعادة الفعلية وتجربة اعتماد الخادم في staging شروطاً قبل النشر؛ لا تعني هذه الدفعات اكتمال المرحلة تشغيلياً.

التبعيات: المرحلة 1. `routes/index.ts`, `socket.ts`, `controllers/trials.controller.ts`, `controllers/invoiceDraft.controller.ts`, `utils/tenantFirebase.ts`.

- جرد المداخل الذي ينتجه `scripts/audit-source.cjs` أساس قائمة المراجعة؛ يضاف له Socket والأعمال الخلفية إن وجدت.
- كل API ما عدا الدخول والصحة يحتاج هوية وعضوية؛ صلاحيات الإدارة مستقلة عن إدارة الشركة.
- فصل مراجع `control` عن بيانات الشركات، وحصر `rootRef` داخل خدمات إدارة مع صلاحية صريحة.
- غلق تسريب `/api/ai/allData` ووضع صلاحية واستحقاق ومقدار بيانات محدد لطلبات AI.
- منع إنشاء/حذف الشركات غير المصرح، ومراجعة عمليات الترحيل التي تعمل عبر GET.
- عولج `GET /api/account/get-account`: صار قراءة فقط، مع تهيئة صريحة تضيف الحسابات الناقصة وتحافظ على الموجودة، وتهيئة الشركات التجريبية أثناء التجهيز.
- مصادقة Socket من رمز موثق وعضوية؛ لا يقبل المستخدم والشركة من query كهوية. حدّث الاتصال عند إلغاء الجلسة.

شرط الخروج: A لا يقرأ أو يغير B عبر القائمة/السجل/التصدير/المسودة/Socket، ومعرفة `id` لا تمنح وصولاً. التراجع يحافظ على حدود الشركات؛ لا يعيد ترويسات الهوية غير الموثقة.

## 3 — مستودعات وتوجيه البيانات ونقل المسارات

**حالة التنفيذ المحلي:** أُضيف `tenantResolver` و`tenantDatabaseProvider` للقاعدة المشتركة، مع ربط الوصول بالسياق ورفض إعادة استخدامه في شركة أخرى. نُقلت قراءات الهوية والعضوية والاستحقاق إلى REST دون رجوع إلى ذاكرة SDK، ثم أُضيفت كتابة المستودعات والسيارات الإدارية المشروطة مع الأرشفة وإسناد السائق المرجعي وواجهة الإدارة. الخادم يحتاج Node >=22.19.0 واعتماد Google في الإنتاج. مرجع القراءات `tenant-data-provider.ar.md`، ومرجع الكتابات `warehouse-writes.ar.md`، ونتائج 120 اختباراً للخادم و6 للمحاكي الفعلي وتجهيز فحص staging في `emulator-and-staging.ar.md`. لا نقل لبيانات العملاء أو قواعد مخصصة؛ بقية الوحدات والمعاملات المالية لم تنتقل، وstaging لم يُختبر فعلياً.

التبعيات: المرحلتان 0 و2 قبل أي نقل فعلي أو نشر. أصبحت ملفات `tenancy/tenantResolver.ts`, `tenancy/tenantDatabaseProvider.ts`, و`repositories/warehouses.repository.ts` موجودة؛ تستكمل المستودعات لكل وحدة تدريجياً.

- أضف واجهة مستودع مقيد بسياق موثوق؛ لا تمرر رابط قاعدة أو بيانات اعتماد من الواجهة.
- المرحلة الأولى تستخدم القاعدة المشتركة فقط. خريطة التوجيه تحتوي مفتاح إعداد خادم، ولا تحتوي أسراراً قابلة للعرض أو التعديل من الشركة.
- ابدأ بالقراءات ثم الكتابات في وحدة واحدة، مع الحفاظ على عقد API والسلوك المالي المثبت بالاختبارات.
- أي نقل للمصدر يتم عبر `copy → verify → catch up/freeze → switch`؛ نسخة مخطط وسجل دفعات وبصمات وتحقق مراجع.
- فك الارتباط بأسماء المستودعات القابلة للتغيير تدريجياً؛ لا تعِد تسمية مفاتيح المخزون أثناء نقل المستأجر.

شرط الخروج: لا دالة أعمال تستطيع اختيار مستأجر أو قاعدة من حقل طلب خام، ومجاميع/مراجع البيانات سليمة قبل التحويل وبعده. لا حذف للمصدر قبل فترة تحقق واستعادة.

## 4 — ثبات المحاسبة ومنع التكرار

الملفات: `functions/transactions.ts`, ومتحكمات `sells`, `purchases`, `payments`, `account`, `journalEntries`, `products`, `transfer`, `materialReservations`, `vehicles`، و`services/transaction.ts`, `services/offlineSales.ts`, `lib/offlineStore.ts` في الواجهة.

- معرّف عملية ثابت عند إنشاء الطلب أو وضعه في الطابور المحلي، ومفتاح idempotency مقيد بالشركة مع بصمة الحمولة. نفس المفتاح بحمولة مختلفة يُرفض.
- وثق المصدر المحاسبي المرجعي وصيغة قيود البيع والقبض والمردود والنقل. الأرصدة المجمعة قابلة للمصالحة مع القيود ولا تسمح للوحدات بتجاوز الترحيل.
- عرّف حالات العملية ومعرّفات نواتجها وإجراء التعافي. توليد UUID جديد عند إعادة محاولة أثر سبق تنفيذه لا يُعد تعافياً.
- قرر حدود الالتزام في RTDB باختبارات تنافس حقيقية في محاكي: `update` متعدد المسارات ذري داخل القاعدة لكنه لا يجعل معاملات منتجات مستقلة ثم دفعة وقيد سلسلة ذرية واحدة.
- امنع فقد تحديثات الحسابات واستنزاف المخزون عند التزامن. اختبر فشل كل خطوة وحالة انقطاع رد ناجح.
- ثبت القيود المرحلة وأضف التصحيح/العكس وسجل الفاعل والسبب. لا تصحح التاريخ المحاسبي تلقائياً أثناء الهجرة.
- المبيعات المؤجلة تحمل الشركة والفاعل والعملية؛ لا تُرسل عند تبديل المستخدم أو الشركة.
- اربط مفاتيح React Query وIndexedDB بالشركة، وأعد توصيل Socket عند تبديلها.

شرط الخروج: البيع والدفع المكرر لا يتكرر أثره، لا نجاح كاذب للنقل، وكل فشل له حالة ظاهرة قابلة للمصالحة. اختبارات الذاكرة الحالية غير كافية لإثبات التزامن أو Security Rules.

## 5 — الصلاحيات والتخصيص

- `allowed = activeMembership + actionPermission + companyEntitlement + recordOwnership` مع سياسة الاشتراك.
- الواجهة تستلم القدرات الفعالة المنقحة؛ يعاد فحص السماح عند كل إجراء خادم.
- صنف الطلبات: إعداد، حقل إضافي، وحدة اختيارية، استراتيجية أعمال، أو استثناء محصور بواجهة صريحة وصيانة موثقة.
- الحقول الإضافية محددة المفاتيح والأنواع والمواقع والنسخة؛ لا تستطيع تغيير القيد أو المجموع المالي بحرية.
- ميزة السائقين/المركبات أول نموذج لوحدة اختيارية، مع اختبارات تفعيلها لشركة ورفضها لأخرى.
- إعدادات قابلة للترقية وتفعيل تدريجي وإيقاف آمن، دون شروط بأسماء العملاء في منطق الأعمال.

## 6 — التشغيل التجاري

- تجهيز شركة بحالة `provisioning` ثم `active` بعد تحقق الحسابات والأدوار والإعدادات؛ إعادة محاولة التجهيز لا تكررها.
- سياسة اشتراك وانتهاء ومهلة سماح واضحة، مع سجل تغييرات وواجهة مالك الشركة.
- نسخ آلي ومراقبة نجاحه واستعادة دورية لشركة، وتوثيق RPO/RTO المقاسين.
- قياس حجم وتنزيلات البيانات وزمن API وأخطاء العمليات لكل شركة دون تسجيل رموز أو بيانات فواتير حساسة.
- صلاحية منفصلة للمشرف العام، وتحديد معدل لمسارات الدخول والتجارب وAI، وstaging وإصدارات قابلة للرجوع.

## 7 — عزل قاعدة اختياري

لا يبدأ لطلبات تخصيص الواجهة. يبدأ لشرط تعاقدي أو حمل مثبت أو هدف استعادة مستقل. استخدم نفس API والمستودعات وخدمة المحاسبة؛ أضف وجهة إلى المزوّد ثم اختبر ونقل شركة واحدة. تقيّم PostgreSQL لاحقاً إذا أثبتت متطلبات المعاملات والتقارير الحاجة إليها، دون نقل فوري الآن.
