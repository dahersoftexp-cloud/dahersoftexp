# جرد البيانات وإثبات الاستعادة قبل الهجرة

هذه إجراءات تشغيل مقترحة. لم تُنفّذ على الإنتاج في الدفعة الأولى. أدوات هذا المستودع تقرأ ملفات محلية فقط، ولا تتصل بقاعدة بيانات ولا تستعيد ملفات إليها.

أُضيفت لاحقاً [تجربة استعادة منفذة لشركة اصطناعية داخل محاكي RTDB الفعلي](emulator-and-staging.ar.md)، مع Gzip وبصمة كاملة وعدم تغير الشركات الأخرى. أداة `audit-backup.cjs` نفسها تبقى محلية للقراءة فقط. النسخ والاستعادة الفعليان لبيانات العملاء وبيئة staging السحابية لم يُنفذا.

## قبل استخراج البيانات

1. سجّل مشروع Firebase واسم instance والمنطقة ونسخة الخادم والواجهة و`TENANTS_ROOT` و`DEFAULT_TENANT_ID` الفعليين. لا تضع بيانات اعتماد في السجل.
2. ثبّت مكان ملكية السجلات: مستخدمو `users` الجذرية، بيانات `tenants/default`، شركات `trialTenants`، وأي مجموعات أعمال قديمة في الجذر. لا تستنتج الملكية من تشابه اسم المستخدم واسم الشركة.
3. احفظ نسخة القواعد المنشورة وسجل إعدادات النشر في مكان آمن. قواعد الوصول غير موجودة في المستودع الحالي.
4. جهّز بيئة staging منفصلة عن الإنتاج بهوية اعتماد محدودة. الخادم المحلي الذي يقرأ `.env` الإنتاجية لا يُعد بيئة معزولة.
5. حدد نافذة snapshot متسقة: قد يلزم إيقاف الكتابات فترة قصيرة وجرد المبيعات المؤجلة. سجل وقت إيقافها وإعادتها. مقارنة ملفين التُقطا أثناء تغيّر البيانات لا تصلح وحدها للتحقق من هجرة.
6. خذ نسخة كاملة من البيانات والقواعد، واحفظ الأصل خارج المستودع. راجع صلاحية النسخة وأحجامها دون عرض كلمات مرور أو سجلات عملاء في السجلات.

مرجع Firebase الرسمي: https://firebase.google.com/docs/database/backups

## فحص ملفات محلية

استبدل المسارات بمجلد آمن خارج Git. دعم `.gz` يتعرف على ترويسة gzip. الأداة تحتاج أن يتسع الملف بعد فك الضغط في ذاكرة الجهاز.

```powershell
node scripts/audit-backup.cjs --input 'D:\DaherBackups\before.json.gz' --scope database
node scripts/audit-backup.cjs --input 'D:\DaherBackups\before.json.gz' --scope database --compare 'D:\DaherBackups\restored.json'
```

لملف استُخرج من عقدة شركة واحدة دون جذر `tenants`:

```powershell
node scripts/audit-backup.cjs --input 'D:\DaherBackups\company-a.json' --scope tenant --tenant-id company-a
```

إذا كان جذر الشركات مختلفاً، مرّر `--tenants-root` بالقيمة الفعلية. لا تُطبع محتويات السجلات أو كلمات المرور. قد يحتوي التقرير معرفات الشركات؛ احفظه في مكان محدود الوصول أيضاً.

- رمز خروج `0`: اكتمل الفحص، والملفان متطابقان بنيوياً إذا استُخدم `--compare`.
- رمز خروج `2`: اكتمل الفحص وظهر اختلاف.
- رمز خروج `1`: ملف/وسيط غير صالح أو تعذرت القراءة. لا يُطبع الملف أو نص خطأ JSON الذي قد يحتوي بيانات منه.

تُحسب SHA-256 لكل شجرة شركة وللمجموعات المعروفة، مع ترتيب ثابت لمفاتيح الكائنات. ترتيب القوائم وقيم البيانات يؤثران على النتيجة. تدخل الحقول والوحدات غير المعروفة في بصمة الشجرة الكاملة أيضاً، ولا يُطبّع معرف الشركة لأن التطبيع قد يخفي تصادماً.

عدد `childCount` عدد الأبناء المباشرين؛ قد تكون `settings` كائناً وليست مجموعة سجلات. `productRecordCount` يعتمد البنية الحالية `products/{warehouse}/{product}`، و`journalLineCount` يعد أسطر القيود. الأداة لا تعيد احتساب الأرصدة ولا تزعم مطابقة محاسبية.

## تجربة الاستعادة

1. استعد النسخة إلى قاعدة staging الفارغة حصراً باستخدام إجراءات Firebase المناسبة.
2. صدّر نتيجة الاستعادة وافحص الملفين بالأمر السابق. لا توجه رابط API الإنتاج إلى قاعدة التجربة.
3. افحص سجلات تمثل بيعاً نقدياً وآجلاً، دفعة، مردوداً، نقل مستودع ومسودة. قارن ربط الفواتير بالعملاء والدفعات والقيود وعدد المنتجات في كل مستودع.
4. قارن المجاميع المالية بنفس قواعد العملات والتقريب المستخدمة في البرنامج، واعزل أي اختلاف قديم. لا تصحح اختلافاً تاريخياً أثناء نقل المسار.
5. اختبر استعادة شركة واحدة إلى موقع staging دون تغيير بصمات الشركات الأخرى. سجل الخطوات والمدة واسم المنفذ والنسخ المستخدمة.
6. حدد RPO (مقدار البيانات المقبول فقدها) وRTO (المدة المقبولة للاستعادة) وفق نتيجة التجربة؛ لا تُعطِ وعداً للعملاء قبل القياس.

## الرجوع أثناء ترحيل لاحق

انسخ دون حذف، تحقق، ألحق التغييرات أو أوقف الكتابات لفترة متفق عليها، ثم حوّل شركة واحدة. احتفظ بتوجيه المسار السابق ونسخته. إذا بدأت كتابات على الوجهة الجديدة فلا يكفي تحويل القراءة إلى المصدر القديم: يجب إيقاف الكتابة وإرجاع الفارق الموثق أولاً لمنع فقد فواتير جديدة. لا تُستخدم الكتابة المزدوجة قبل وجود سجل عمليات ومصالحة واختبار للفشل الجزئي.

## اختبار smoke القديم

الأمر `npm test` هو الاختبار الآمن الافتراضي. لا يتضمن `live-api-smoke.js`.

اختبار smoke القديم يعدّل ويحذف سجلات ويستدعي مسارات ترحيل، ويتضمن افتراضات قديمة عن إدارة المستخدمين. تشغيله مؤجل حتى إصلاح الهوية. حتى بعد ذلك، يلزم قاعدة محلية قابلة للحذف، وعنوان loopback صريح، و`SMOKE_ALLOW_WRITES=isolated-test-database`، وشركة بادئة معرفها `qa-smoke-`.

التحقق من URL وإقرار البيئة لا يثبتان أن إعداد الخادم معزول؛ افحص وجهة قاعدة الخادم قبل التشغيل. يمنع السكربت اتباع التحويلات HTTP ويوقف بقية الكتابات عند فشل تطابق الشركة في تسجيل الدخول.
