# الدفعة الثالثة: صلاحيات المداخل وحماية القراءات

**تحديث لاحق:** عالجت الدفعة الرابعة قراءات الهوية والعضوية بوسيلة REST لا ترجع إلى ذاكرة SDK، وبدأت مستودع استعلام المستودعات. راجع [التنفيذ وإعداد الاعتماد وحدود الاختبار](tenant-data-provider.ar.md). الأرقام ووصف القيود أدناه يسجلان حالة الدفعة الثالثة عند إنجازها.

حالة هذه الدفعة: تنفيذ محلي في الخادم والواجهة، دون نشر أو اتصال ببيانات العملاء. تعتمد على دفعة الهوية والعضوية، وتنفذ جزء حراسة الإجراءات من المرحلة 2. لا تغلق بوابات النسخ والاستعادة أو مراجعة القواعد المنشورة.

## سياسة السماح

يمر كل طلب `/api` عبر التحقق من الجلسة والعضوية، ثم `auth/authorization.ts` قبل دخول المتحكم. الاستثناء العام الوحيد هو `POST /auth/login`؛ الصحة `/` خارج API. أضيفت سياسة صريحة لكل إعلان API حالي: 93 إعلاناً، بما فيها تهيئة الحسابات الجديدة والمساران المتقاعدان. HEAD يستخدم سياسة GET، وحالة الأحرف والشرطة النهائية تتبع مطابقة Express. المسار بلا سياسة يرفض بـ `403 API_POLICY_REQUIRED` حتى لمدير الشركة. اختبار الجرد يرفض إضافة مسار دون سياسة أو إبقاء سياسة لمسار محذوف.

المصدر الموثوق للدور والصلاحيات هو سجل العضوية المقروء على الخادم. تغيير صلاحية في قاعدة البيانات يؤثر في الطلب التالي عند نجاح قراءة حديثة؛ لا تؤخذ الصلاحيات من JWT أو ترويسات الطلب أو محتوى المتصفح. تبقى ملاحظة حداثة قراءة Firebase SDK أدناه مهمة.

- مدير الشركة يستطيع إجراءات شركته، وتظل إدارة المنصة والاستحقاقات منفصلتين عنه.
- غير المدير يحتاج صلاحية الإجراء، مثل `sales.read` أو `sales.create`، أو صلاحية صفحة موجودة يمنحها جدول `actionPages` لذلك الإجراء. صلاحية `sales.read` وحدها لا تمنح إنشاء أو تعديل البيع.
- محرر المستخدمين الحالي يوزع صلاحيات الصفحات. تسمح طبقة التوافق لكل صفحة بقراءة تبعياتها وتنفيذ عملياتها الحالية؛ هذه ليست بعد واجهة توزيع مفصلة لكل إجراء.
- صلاحية `home` أو `dashboard` تتضمن البيانات المالية التي تعرضها هاتان الصفحتان حالياً؛ لا تمنحها لموظف تريد حجب هذه المعلومات عنه. لا يُستنتج وصول مالي من مجرد كونه عضواً.
- الحساب القديم الذي لا يحتوي أي حقل صلاحيات يحصل على صفحات دوره القديمة: `user → home,dashboard,products`، و`driver → driver-sales`. قائمة صريحة فارغة تبقى بلا صلاحيات. الحسابات المركزية الجديدة لا تحصل على هذه الافتراضات.
- `tenants.manage` من الهوية المركزية، أو حساب المنصة القديم المحدد في إعداد الخادم والمقيد بشركته، شرط مستقل لمسارات التجارب. لا تمنح صفحة أو عضوية شركة هذا الامتياز.
- إدارة السيارات والمستخدمين وترحيل العملات تبقى لمدير الشركة كما في المتحكمات الحالية. بيع السائق يمر عبر مسار سيارته الذي يفحص ارتباطه بها؛ صلاحية السائق لا تفتح مسار البيع العام.
- حذف المنتج وتعديل الأسعار بالجملة لا يُمنحان بصلاحية صفحة المنتجات وحدها؛ يلزمان دور المدير أو صلاحية الإجراء الصريحة المقابلة.

الملف المرجعي الكامل لربط المداخل بالإجراءات هو `src/auth/authorization.ts`، ويجب مراجعته مع أي ميزة جديدة. العمليات التي تمزج المخزون والمحاسبة ما زالت تحتاج مرحلة ثبات المحاسبة، حتى لو أصبح استدعاؤها محكوماً بصلاحية.

## البيانات المرجعية دون كشف أرصدة

لحفظ عمل شاشات البيع والشراء دون منح صلاحية تقارير كاملة، تستخدم قوائم الزبائن والموردين والحسابات إسقاطاً محدد الحقول في `auth/resourceViews.ts`:

| القائمة | من يملك صلاحية القائمة الكاملة | من يحتاج الاختيار داخل عملية أخرى |
| --- | --- | --- |
| الزبائن | الاستجابة القائمة كاملة ضمن شركته | الاسم والمعرف والرقم والحسابات الافتراضية فقط |
| الموردون | الاستجابة القائمة كاملة ضمن شركته | الاسم والمعرف والرقم والحسابات الافتراضية فقط |
| الحسابات | الحقول القائمة بما فيها الأرصدة | المعرف والاسم والرمز والنوع والفئة والعملة والحالة اللازمة للاختيار |

تُستبعد الحقول الخاصة الجديدة تلقائياً من القوائم المختصرة. مسارا تفاصيل الزبون والحساب لا يقبلان صلاحية الاختيار وحدها. إنشاء زبون أو مورد من صلاحية عملية أخرى لا يقبل حقن أرصدة أو قوائم فواتير؛ تُنشأ الأرصدة بصفر وتُنتقى الحقول التعريفية فقط. احتُفظ بعقد إنشاء مدير الزبائن/الموردين الحالي حتى مراجعة الأرصدة الافتتاحية في مرحلة المحاسبة.

تفاصيل المنتج لا تعيد مشترياته أو مبيعاته أو تحويلاته إلا بصلاحيات السجل المقابلة. استعلام المستودع يطبق سياسة إخفاء الأسعار الحالية أيضاً. يلزم لاحقاً توحيد سياسة أسعار التكلفة والبيع على مستوى الحقل في كل DTO، ومراجعة إسقاط بيانات التقارير الأوسع؛ هذه الدفعة لا تدعي إعادة تصميم جميع عقود الاستجابة.

الواجهة تستعمل التخزين المؤقت للمنتجات والزبائن والحسابات عند فشل اتصال معروف فقط. رفض 401/403 أو خطأ تبديل الجلسة لا يعاد تفسيره كعمل دون إنترنت ولا يستبدل بنتيجة قديمة. هذا لا يمحو ما سبق تنزيله أو عرضه، ولا يحول التخزين المحلي إلى مصدر صلاحيات؛ تحديث القدرات الفعالة وإبطال كل العرض المؤقت عند سحب صلاحية جزء لاحق من المرحلة 5.

## المداخل التي تغير سلوكها

| المدخل | السلوك الجديد |
| --- | --- |
| `GET /api/ai/allData` | `410 ENDPOINT_RETIRED` دون قراءة جذر الشركة، حتى للمدير |
| `GET /api/warehouses/migrate` | `410 ENDPOINT_RETIRED` دون أي ترحيل |
| `GET /api/account/get-account` | قراءة فقط؛ لا يعيد تسمية الحسابات أو تفعيلها ولا يكتب أثناء العرض |
| `POST /api/account/initialize-defaults` | مدير الشركة فقط؛ يضيف الحسابات الأساسية المفقودة بمعاملة على مجموعة الحسابات |

تهيئة الحسابات تعتبر الحساب موجوداً إذا تطابق المعرف الأساسي أو الرمز. لا تغير الاسم أو العملة أو الحالة أو الرصيد أو أي حقل في حساب موجود، ولا تنشئ نسخة ثانية عند تكرار الطلب. أضيف زر «إضافة الحسابات الأساسية الناقصة» مع تأكيد واضح في صفحة الحسابات للمدير. الشركات التجريبية الجديدة تستمر في الحصول على حساباتها أثناء التجهيز. الشركات القديمة تحتاج جرد الحسابات في staging قبل الطرح؛ لن تُصلح حساباتها أو تُعاد تسميتها تلقائياً عند عرض الصفحة.

تقاعد ترحيل المستودعات مقصود؛ المتحكم القديم لم يعد مربوطاً بالتنفيذ. إعادة تقديم هذه الوظيفة تحتاج أداة ترحيل بخطة ومعاينة وسجل وتحقق أسماء ومعرفات وتراجع. ترحيل العملات القائم محمي بدور المدير، ولا يُشغَّل في هذه الدفعة؛ آثاره التاريخية تحتاج مراجعة المرحلة 4.

## الذكاء الاصطناعي

كل مسار AI عامل يحتاج صلاحية `ai.read` أو `ai.write` المناسبة (مدير الشركة يملك صلاحية الإجراء)، وكذلك قيمة منطقية صريحة:

```text
control/companies/{tenantId}/entitlements/ai = true
```

غيابها أو كونها `false` يرفض بـ `403 FEATURE_DISABLED` حتى لمدير الشركة. لا توجد في هذه الدفعة واجهة لتغيير استحقاق الشركة، ولا يُقبل الاستحقاق من بيانات الطلب أو إعدادات الشركة التي يستطيع موظفوها تعديلها. التفعيل التشغيلي لاحقاً من إدارة المنصة بعد الاتفاق على نقل بيانات أعمال مختارة إلى المزود وإعداد الخادم. لا تُنسخ الاستحقاقات من قالب تجربة.

طلب السؤال يقرأ فقط `products,sells,purchases,customer,supplier,payment,returns,accounts,warehouses` داخل الشركة. لا يقرأ جذرها أو المستخدمين أو المسودات أو الإعدادات، وينتقي حقول السياق قبل الإرسال. حُذف رقم الهاتف من سياق الأطراف. الحدود الحالية:

- سؤال حتى 2000 محرف و8000 بايت UTF-8.
- مصدر أعمال حتى 5 MiB بعد جلب المجموعات، وإلا يرفض قبل الاتصال بالمزود.
- سياق JSON حتى 60000 بايت UTF-8؛ تُختصر القوائم تدريجياً مع بيان الاختصار، وتبقى المجاميع محسوبة من المصدر الكامل المقبول.
- خمس محاولات في الدقيقة وعملية جارية واحدة للشركة في عملية الخادم الواحدة؛ يعاد السماح بالعملية الجارية عند نهاية الطلب.
- مهلة اتصال المزود 30 ثانية، وردود أخطاء المزود وتفاصيلها لا تصل إلى العميل.

**حد تشغيلي قائم:** القراءات التسع ما زالت تجلب مجموعات كاملة من RTDB قبل فحص حجمها. سقف 5 MiB ليس حداً للتنزيل أو الذاكرة أثناء الجلب. قبل تفعيلها لشركات كبيرة، يلزم مستودع تحليلات بمجاميع مؤرخة وقراءات مقسمة؛ لا نرسل ملخصاً مالياً مضللاً محسوباً على عينة غير معلنة. محدد المعدل في الذاكرة يحتاج مخزناً مشتركاً قبل تشغيل عدة نسخ من الخادم.

تحديث التقرير في الواجهة صار يطلب `/api/ai/ask` عبر Axios الموثق للشركة. أزيل طلب رابط n8n الثابت الذي لا يحمل سياق شركة موثقاً. أي تكامل n8n خارجي يستعمل `allData` أو يفترض مداخل عامة يجب مراجعته وإعطاؤه هوية خدمة محدودة لاحقاً؛ لا يعاد فتح التصدير العام لتوافقه.

## Socket وحدود مراجع البيانات

مزامنة المسودة تحتاج `draft.use` عند الاتصال، وعند كل حزمة، ولدى المتلقين قبل بث تحديث. تستمر مراجعة العضوية وانتهاء الرمز، والعزل بالغرفة المقيدة بالشركة والمستخدم. سحب صلاحية البيع يمنع تحديث المسودة عبر Socket أيضاً.

أزيل `rootRef` من غلاف بيانات الأعمال `tenantFirebase.ts`. مراجع الجذر صارت في `tenancy/controlDatabase.ts` وتستخدمها خدمة الحسابات وإدارة التجارب فقط. حجز ملف المستخدم الجديد انتقل إلى خدمة الحسابات. اختبار المصدر يمنع إدخال اعتماد SDK قاعدة البيانات أو غلاف الجذر إلى متحكم أعمال جديد. هذا حد داخل الكود؛ لا يغني عن Security Rules أو تغيير طريقة اتصال الخادم بقاعدة البيانات.

## التحقق وخطة الطرح

الفحوص المحلية تغطي مطابقة كل مدخل لسياسة، ورفض عمليات مالية دون كتابة، وبيعاً فعلياً بصلاحية كاشير ثم سحبها، وتغير الصلاحيات مع نفس الرمز، والقوائم المختصرة وحقن الحقول، وتقاعد التصدير والترحيل، وحفظ الحسابات عند القراءة والتهيئة المتكررة، وحراسة Socket، واستحقاق AI وحدود السياق وأخطاء مزوده. تُستبدل Firebase ببيانات ذاكرة اصطناعية ويُستبدل اتصال AI باستجابة محلية؛ لا تُستخدم قاعدة العملاء أو خدمة AI حقيقية.

نتيجة التحقق المحلي لهذه الدفعة:

- الخادم: `npm test` نجح في 68 اختباراً مع بناء TypeScript.
- الواجهة: `npm test` نجح في 21 اختباراً، و`npm run build` نجح.
- `git diff --check` نجح في المستودعين.
- الفحص الكامل `npx tsc -p tsconfig.app.json --noEmit --pretty false` في الواجهة ما زال يفشل بسبب أخطاء سابقة، منها نوع `selectedPriceType` في جدول البيع وحقول `Sell.totalUSD/totalSYP` في Home وأنواع TrialBalance ومتغيرات غير مستخدمة. بقيت تحذيرات الصفحة القائمة في ChartAccount أيضاً؛ لم يضف إجراء التهيئة أخطاء أنواع جديدة. بناء Vite الناجح لا يعوض هذا الفحص.

قبل النشر:

1. إغلاق جرد الإنتاج والنسخ والاستعادة ومراجعة القواعد المنشورة الموضحة في `baseline-and-recovery.ar.md`.
2. مراجعة جميع المستخدمين والصلاحيات الممنوحة في staging، خصوصاً الحسابات التي تحمل قائمة فارغة وصفحات الملخصات المالية. تجربة بيع وشراء وقبض ومردود وسائق بصلاحيات الموظفين الفعلية.
3. مقارنة الحسابات الموجودة قبل وبعد القراءات؛ عرض الإجراء الصريح للحسابات الناقصة وتجربته على النسخة المعزولة فقط. فحص أي اعتماد على GET القديم لترحيل المستودعات.
4. إبقاء AI معطلاً حتى مراجعة استحقاق الشركة وتكاملاتها الخارجية وحجمها.
5. معالجة حداثة قراءة الهوية: SDK JavaScript المستخدم قد يرجع قراءة مخبأة عند تعذر الخادم. اختبارات الذاكرة لا تثبت سحب الصلاحية أثناء عطل الشبكة؛ يلزم حل خادم بقراءة موثوقة واختبار فشل حقيقي قبل الاعتماد التجاري.
6. نشر الخادم والواجهة المتوافقين على staging، ثم مقارنة المجاميع المالية واختبار الإلغاء والرجوع. لا نرجع إلى إصدار يلغي حراسة الإجراءات أو لا يفهم كلمات المرور المجزأة.

العمل التالي: مستودعات ومزوّد بيانات للشركة على القاعدة المشتركة، بدءاً بقراءات وحدة واحدة، مع استكمال بوابات الإنتاج أعلاه. بعدها منع تكرار العمليات وثبات المحاسبة، ثم واجهة القدرات والاستحقاقات والتخصيص لكل شركة، بدءاً بوحدة السيارات والسائقين. لم يبدأ فصل قاعدة لكل شركة أو نسخ كود لكل عميل.
