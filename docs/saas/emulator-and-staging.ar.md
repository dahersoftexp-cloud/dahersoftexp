# الدفعة السادسة: إثبات المحاكي وتجهيز فحص staging

التاريخ: 2026-10-17. هذه الدفعة تستكمل بوابة التحقق المحلية داخل المرحلة 3. نجح الاختبار على **Firebase Realtime Database Emulator الفعلي**، وأُعد فحص إعدادات staging والقراءة عبر اعتماد الخادم. لم تُنشأ موارد سحابية أو تُستعد بيانات عملاء أو يُنشر إصدار.

## النتائج المنفذة

| الفحص | النتيجة |
| --- | --- |
| `npm test` في الخادم | **120 اختباراً ناجحاً**، مع بناء TypeScript |
| `npm run emulators:warehouse` | **6 اختبارات ناجحة** على RTDB Emulator `4.11.2` مع Firebase CLI `15.34.0` |
| قواعد المحاكي | تحميل ملف القواعد المخصص للاختبار، ورفض المسارات خارج شركات `qa-warehouse-*` |
| استعادة نسخة محلية | تصدير شركة اصطناعية إلى Gzip، واستعادتها إلى شركة اختبار جديدة، وتطابق SHA-256 للشجرة المصدرة |
| عزل الاستعادة والأرشفة | بقاء بصمة الشركة المصدر والشركة المجاورة، وحفظ كمية المخزون بعد أرشفة المستودع المستعاد |
| سلوك الحفظ المشروط | نجاح دمج حقلين مختلفين بعد تنافس حقيقي، وزيادة النسخة دون فقد تحديث، ورفض نموذج قديم |
| حفظ الأولويات | تأكيد عمل `format=export` مع `ETag` وحفظ أولوية السجل والاسم بعد التعديل |
| الإنشاء المتزامن | إنشاء واحد للاسم المطبع نفسه |
| فقدان إقرار الحفظ | حقن خطأ اتصال بعد التزام المحاكي؛ رجوع نتيجة مجهولة، ومحاولة كتابة واحدة، ثم قراءة السجل ورفض تكراره |

لا تغييرات في الواجهة أو منطق الأعمال الإنتاجي بهذه الدفعة. نتيجة الواجهة من الدفعة السابقة 25 اختباراً وبناء Vite ناجح؛ لم يُعد تشغيلهما هنا. أخطاء فحص الأنواع السابقة وبوابات المحاسبة والتخصيص والتشغيل باقية.

الأرقام تخص بيانات اصطناعية صغيرة. لا تثبت حمل جميع الشركات أو صحة تاريخ محاسبي فعلي أو مدة استعادة متفقاً عليها مع العملاء. اعتماد Google وIAM والقواعد السحابية المنشورة لم تُختبر بهذه التجربة المحلية.

## تشغيل محلي قابل للإعادة

أُكمل تنزيل Java محمولة داخل مخزن أدوات المستخدم، دون تثبيت عام أو تغيير دائم لـPATH:

- المجلد: `%LOCALAPPDATA%\DaherSoftTestTools\zulu21`.
- النسخة المستخدمة: Azul Zulu JRE `21.0.12.1`، من CDN الرسمي. طابقت SHA-256 بيانات [حزمة Azul الرسمية](https://api.azul.com/metadata/v1/zulu/packages/a51c4f91-61c6-4b26-9060-a2b12745e236/): `37ad372b04da388c326f0507abec38b8e1d11e3bddf6128b215c8f0a06ff8177`.
- ملف المحاكي داخل `%LOCALAPPDATA%\DaherSoftTestTools\emulators`، وطابقت SHA-256 بيانات Firebase CLI المثبت: `b70d99344caf17c98b6f910fa8f6edf32a7c016cb1035e8915f70d38901eb97f`.

من مستودع الخادم، على هذا الجهاز:

```powershell
$emulatorJavaExe = Get-ChildItem -LiteralPath "$env:LOCALAPPDATA\DaherSoftTestTools\zulu21" -Filter java.exe -Recurse -File | Select-Object -First 1 -ExpandProperty FullName
if (!$emulatorJavaExe) { throw 'Portable Java is missing' }
$env:DAHERSOFT_TEST_JAVA_HOME = Split-Path -Parent (Split-Path -Parent $emulatorJavaExe)
$env:DAHERSOFT_TEST_EMULATOR_CACHE = Join-Path $env:LOCALAPPDATA 'DaherSoftTestTools\emulators'
$env:DAHERSOFT_EMULATOR_OFFLINE = '1'
npm run emulators:warehouse
```

متغير `DAHERSOFT_EMULATOR_OFFLINE=1` يستخدم نسخة CLI الموجودة مسبقاً في مخزن npm؛ على جهاز جديد يُترك غير مضبوط للسماح بتنزيل النسخة المثبتة في الأمر. يحتاج الجهاز الجديد Java 21 من مصدر موثوق، ويقبل المشغّل `JAVA_HOME` أو `DAHERSOFT_TEST_JAVA_HOME`. تستخدم مهمة CI تعريف Java الموجود فيها، ولم تُشغّل GitHub Actions عن بُعد.

المشغّل الجديد `scripts/run-warehouse-emulator.cjs` يثبت مشروع `demo-dahersoft-warehouse` وملف إعداد المحاكي. يرفض تغيير الارتباط `127.0.0.1:19000` أو قواعد الاختبار أو تمرير وسائط إضافية لاختيار مشروع آخر. ينقل إلى العملية بيئة تشغيل محددة، فتظل إعدادات قاعدة الخادم واعتماده وأسراره وأعلام تصحيح الوكيل خارج بيئة CLI وسجلاته. يحمل CLI بيئة demo اللازمة لعملية الاختبار الفرعية.

اختبارات المستودعات تستخدم مزوّد البيانات الفعلي وREST نحو المحاكي. اعتماد التطبيق ومداخل الأعمال الأخرى المستوردة في مساعد الاختبار تبقى معزولة ببديل SDK؛ لم يُدعَ أن كل وحدات البرنامج انتقلت إلى المحاكي أو إلى الطبقة الجديدة. بعد انتهاء الأمر أُغلق المحاكي، ولا توجد قاعدة محلية دائمة لهذا التشغيل.

مراجع التشغيل: [إعداد مجموعة محاكيات Firebase](https://firebase.google.com/docs/emulator-suite/install_and_configure)، و[تشغيل Java المحمولة على Windows](https://docs.azul.com/core/install/windows).

## تجهيز staging

أُضيفت أداة `scripts/staging-preflight.cjs` وملف عام بلا أسرار `staging.example.json`. الأداة تقرأ الملف المحدد وبيئة العملية فقط؛ لا تحمل `.env` أو تشغّل التطبيق.

### إعداد ملف الهدف

1. انسخ [قالب الإعداد](staging.example.json) إلى مكان خارج Git وحدّث القيم العامة.
2. سجل معرف مشروع الإنتاج ورابط قاعدته للمقارنة المحلية فقط. لا تتصل الأداة بهذه الوجهة.
3. سجل معرف مشروع staging ورابط قاعدته المستقلة. تشترط الأداة اختلاف المشروع والقاعدة معاً، وHTTPS على نطاق Firebase الرسمي، وغياب مسار فرعي أو استعلام أو اعتماد في الرابط.
4. اسم instance يجب أن يساوي معرف مشروعه أو يبدأ بمعرف المشروع ثم `-`. هذا حاجز محلي لتقليل خطأ التوجيه؛ فحص الاسم لا يثبت وحده ملكية المشروع سحابياً. instance ذو اسم مخصص لا يطابق الشرط يحتاج إجراء تحقق مستقل قبل توسيع الأداة له.
5. حدد `tenantsRoot` الفعلي و`testTenantId` ببادئة `qa-staging-`. القيم النائبة في القالب مرفوضة، وكذلك حقول أسرار إضافية أو مسارات محجوزة.

### إعداد عملية الفحص

اضبط في بيئة staging نفسها:

| الإعداد | القيمة |
| --- | --- |
| `NODE_ENV` | `production` لتجربة قيود الإقلاع الإنتاجية |
| `FIREBASE_projectId` | مشروع staging في ملف الهدف |
| `FIREBASE_databaseURL` | رابط staging نفسه، الذي يستخدمه SDK وREST |
| `FIREBASE_REST_AUTH_MODE` | `google`؛ أو الافتراضي الإنتاجي المكافئ |
| `TENANTS_ROOT` | الجذر الموجود في الملف، أو الافتراضي `tenants` عند مطابقته |
| `JWT_SECRET` | سر staging مستقل قوي، مركب عبر إعداد الخادم أو مخزن الأسرار |
| ADC | اعتماد خاص ببيئة الاختبار، مضبوط خارج المحادثة وGit |

لا تطبع السر أو رمز OAuth، ولا تضع ملف حساب خدمة ضمن القالب. شرح الاعتماد في [دفعة مزوّد البيانات](tenant-data-provider.ar.md).

### الفحص المحلي والقراءة السحابية

استبدل مسار المثال بملف الهدف المكتمل:

```powershell
npm run staging:preflight -- --config 'C:\DaherSoftStaging\staging.json'
npm run staging:preflight -- --config 'C:\DaherSoftStaging\staging.json' --probe
```

الأمر الأول يفحص الإعدادات دون اتصال شبكي. الثاني، بعد نجاح الفحص، يطلب اعتماد Google ويقرأ فقط:

- `control/companies/{testTenantId}`.
- `{tenantsRoot}/{testTenantId}/warehouses/__staging_probe__` بقراءة الإصدار.

لا تُنشأ شركة أو يُعدّل سجل أو يُرفع ملف قواعد. التقرير يطبع وصف الهدف العام ونجاح القراءة وعدد الكتابات صفر، ويحمل `productionReadinessVerified=false`. نجاح قراءة قيمة `null` يثبت إتاحة المسار للاعتماد، ولا يثبت تجهيز شركة قابلة للدخول أو نجاح الكتابة أو الصلاحيات المالية. أخطاء الشبكة والاعتماد تُختصر إلى رمز ثابت دون تفاصيل خام. لا توجد إعادة محاولة مجهولة الهوية.

أمثلة الرفض: `STAGING_NOT_ISOLATED` لتطابق المشروع أو القاعدة، و`STAGING_RUNTIME_MISMATCH` لاختلاف إعداد الخادم عن الهدف، و`STAGING_RUNTIME_INSECURE` لإعداد إنتاجي غير صالح، و`STAGING_READ_PROBE_FAILED` لتعذر القراءة. اختبارات الأداة تستخدم بدائل اصطناعية؛ لا تُحسب كتجربة فعلية لـOAuth/IAM.

## المتبقي قبل النشر

**الحالة الحالية:** لم يُقدّم ملف هدف staging مكتمل أو معرف مشروع اختبار ورابط قاعدة مستقلان؛ لذلك لم يُشغّل `--probe` على السحابة ولم تُنشأ موارد فيها. طُلبت القيم العامة لاستكمال هذه الخطوة. الاعتماد يبقى في إعداد بيئة التشغيل.

1. تحديد مشروع staging المعزول وإعداد الاعتماد، ثم تشغيل فحص الإعداد والقراءة أعلاه.
2. أخذ نسخة فعلية متسقة من البيانات والقواعد وفق [إجراء النسخ والاستعادة](baseline-and-recovery.ar.md)، واستعادتها في البيئة المعزولة ومقارنتها. تجربة الشركة الاصطناعية في المحاكي لا تغلق هذا الشرط.
3. جرد استثناءات أسماء المستودعات و`revision` والمعرّفات وربط السائقين القديم، ومراجعة IAM والقواعد المنشورة. تستمر بعض الوحدات باستخدام SDK؛ يجب إثبات عملها قبل أي تشديد للقواعد.
4. تجربة API والواجهة والدخول والصلاحيات والبيع والقبض والنقل في staging، ومراجعة الفواتير والمجاميع والأرصدة والمخزون مع عزل الفروق التاريخية. فحص القراءة وحده لا يثبت هذه العمليات.
5. قياس الأداء والاستعادة والحمل، وتجهيز بناء رجوع متوافق مع الأرشفة ونسخة السجل وربط السائق المرجعي. لا نشر قبل إغلاق هذه البوابات.

بعد هذه البوابة تستمر المرحلة 3 بنقل بقية الوحدات، وتتطلب المرحلة 4 منع تكرار العمليات وثبات المحاسبة قبل البيع واسع النطاق. لا يتغير قرار التصميم: إصدار برنامج واحد وقاعدة مشتركة بمسار لكل شركة، مع تخصيصات قابلة للترقية وقاعدة مخصصة اختيارية عند الحاجة.
